# The gauntlet: hundreds of hard tests, with truth from the compiler

2026-11-05 to 2026-11-06. The brief was to make Teslon the strongest tool in
its field, with no corner missed:
- research every kind of change a developer makes, and every technology they
  make it in;
- then test Teslon against hundreds of tests, hard, harder and hardest.

The research is in two documents:
- [CHANGE-ATLAS-2026-11-05.md](CHANGE-ATLAS-2026-11-05.md): 17 families,
  about 150 kinds of change;
- [TECH-LANDSCAPE-2026-11-05.md](TECH-LANDSCAPE-2026-11-05.md): what teams
  build with, and what Teslon reads.

This document is the testing.

## The decision, as a co-owner

Hundreds of tests are worth nothing if their truth is wrong, and until now
every truth was written by hand, by the same project. So this round did two
things.

1. **Truth from the compiler, for volume.** The fixtures are built with javac
   and Maven. Their bytecode is read with `javap` into a call graph, and on
   top of it go the edges the framework makes at run time:
   - Jackson getters and setters;
   - `@Valid` validators;
   - exception handlers, by what a flow can throw;
   - synchronous events;
   - Feign calls to the other service's endpoint;
   - Kafka topics;
   - JPA lifecycle callbacks;
   - beans that every request passes through.

   A hand-written map says which endpoints each screen calls. It was written
   by reading the front end, not taken from Teslon.

   None of this shares code with Teslon. Every mutant is proven by the
   compiler before it counts: it compiles, and its bytecode differs from the
   original in exactly the one method it names, or in none for a comment.
2. **Truth by hand, for hardness.** The change atlas was turned into 32
   super-hard PRs: start-up failures, build settings, production-only
   settings, CSS that escapes its component, and code in languages Teslon
   does not read. The compiler approves every one, and the diff looks
   harmless.

Code: [bench/gauntlet](../bench/gauntlet). The parts:
- `build.sh` compiles a fixture;
- `javap.mjs` reads the bytecode;
- `oracle.mjs` holds the run-time rules;
- `front-edge.mjs` is the screen map;
- `mutate.mjs` makes the mutants;
- `run.mjs` runs and scores them.

CI runs it as the `gauntlet` job.

## What was run

| Set | Tests | What each one is |
|---|---|---|
| Behaviour mutants | 200 (OrderDesk 83, ShopFlow 117) | `if (Thread.interrupted()) throw …` as the first statement of a method. Every method with a body in the app's source gets one |
| Route mutants | 34 (19 + 15) | Each endpoint's path, and each controller's prefix, moved by `/v2` |
| Comment mutants | 200 (83 + 117) | A comment inside each method. The class must compile to the same bytecode, and nothing may be listed to test |
| Super-hard probes | 32 (OrderDesk 18, ShopFlow 14) | Hand-written, truth first, tiered u1/v1 (hard) to u4/v4 (super hardest) |

That makes **466 new tests**. With the existing suites:
- 178 + 79 + 9 probes;
- 33 proving-ground runs;
- 18 bench cases;
- 221 unit tests.

Teslon is now checked against **about 1,000 tests on every change to it**.

**Scoring:**
- **Trust failures:** a wrong skip, a silent area, a failed citation, a
  crash, or a comment-only mutant listed to test.
- **Content:** areas reached only through another thread or a topic are
  reported apart. Teslon lists the job that runs the change; the area that
  sent the message runs nothing changed.

## What it found, and what was fixed

### The first run

| Set | Trusted |
|---|---|
| Behaviour mutants | 200 / 200 (after one oracle fix, below) |
| Route mutants | 34 / 34 |
| Comment mutants | **1 / 200** |
| Super-hard probes | **25 / 32** |

There was no wrong skip on any behaviour or route mutant. But the
compiler-proven noise test and the super-hard PRs found real gaps.

### The gaps, and their fixes

| Found by | What Teslon did | Why | Fix |
|---|---|---|---|
| 199 comment mutants | A comment inside a method listed that method's screens to test | Changed lines were followed with no check that the code itself changed | A method whose tokens, signature and annotations are the same on both sides runs as before, and a file that is the same Java token for token has no effect (`sameCodeLines`, `sameTokens` in `java.ts`, used by the Java, Kafka-producer and data-write analyses) |
| u4-01 a bean moved outside the component scan | Wrong skip of 7 screens | Teslon followed the moved code, not what Spring would make of it | New: [startup.ts](../packages/core/src/engine/startup.ts). A change that stops a service from starting lists every API and job of that service |
| u4-02 `@Service` removed | Every screen held | Read as code nothing reaches | startup.ts: the bean is gone and another bean needs it, so the service does not start |
| u4-03 a constructor asks for a `Clock` | Wrong skip of 8 screens | — | startup.ts: no bean provides it (a JDK type is never a bean unless the app makes one) |
| u4-04 `findByOrderNumber`, and Order has no number | Wrong skip of 12 screens | — | startup.ts parses Spring Data derived queries against the entity's properties |
| v4-02 a Flyway migration numbered below the latest | Wrong skip of orders-service | — | startup.ts: Flyway's validation refuses it; an edited applied migration fails its checksum |
| u4-06 `<parameters>false</parameters>` | **Silent**: "build section, no effect" | The compiler plugin was treated as tooling | The compiler block is now read. With parameter names off, the endpoints whose `@PathVariable` or `@RequestParam` has no name are listed; any other compiler change is said and held |
| u4-08 Kubernetes turns on the prod profile | Wrong skip of the product pages | Deployment files were "their own area" | A deployment that turns a Spring profile on or off follows every setting of that profile's file |
| u4-15 `::ng-deep table` in a component | Wrong skip of the table screens | A component's styles were scoped to its screens | A style that escapes its component (`::ng-deep` with no `:host` before it, or no encapsulation) is global: every screen |

The independent checker (`certify.ts`) learned the same three things:
start-up risks, profiles that a deployment turns on, and style leaks. Its
soundness test still certifies nothing that the truth says is reached:
- OrderDesk: 590 areas;
- ShopFlow: 305 areas.

### What the oracle got wrong, and Teslon got right

The oracle's first run said that `GET /api/invoices` was silent for 15
mutants of Customer, Product and order-line getters. Teslon was right:
`Invoice.order` carries
`@JsonIgnoreProperties({"items", "customer"})`, so the invoice JSON never
holds them. The oracle now reads `@JsonIgnoreProperties` on properties and
classes.

The 64 ShopFlow content skips are of one kind. A billing or notification
method changes, and the oracle counts the screen whose order started the
chain (`/orders/new`) as content. Teslon lists the billing or notification
job, which runs the change. The screen runs nothing changed.

take the new paths, and both answers are right:
- `00e253dc` adds `secret-samples` to `SPRING_PROFILES_ACTIVE` in the
  Docker `app.yml`. Teslon follows the settings of
  `application-secret-samples.yml`.
- `2070b929` (the 8.3 upgrade) changes the compiler settings. Teslon says so
  and holds; before, it said nothing.

## Honest limits

- **The oracle is ours too.** It is a second, independent reading built from
  the compiler's facts, not a proof from a real run. Its own blind spots:
  - reflection;
  - library calls back into app code (`toString` from a logger);
  - data effects, which are counted as content and not scored as trust.
- **Java is where the compiler oracle exists so far.** The front end is
  tested by the hand catalogs. `tsc` and `vue-tsc` are the next oracles.
- **The fixtures are Teslon's own apps.** The pilot on a real team's last 50
  to 100 merged PRs is still the step that proves Teslon on code it has
  never seen.
