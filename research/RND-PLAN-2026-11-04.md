# R&D: the six gaps, who solved what, and the plan

2026-11-04. The pending list from
[EXPECTATION-SCORECARD-2026-11-04.md](EXPECTATION-SCORECARD-2026-11-04.md):
1. React and Next.js.
2. Several repositories at once.
3. A live run on real PRs.
4. Field-level precision on Vue.
5. RabbitMQ, Spring Cloud Stream, GraphQL, gRPC, WebFlux, Spring Batch.
6. Kotlin, then back ends that are not Java.

For each one, this page sets out:
- what "perfect" means for it;
- who solved the nearest problem best, and what we take from them;
- the design for Teslon;
- the fixture and probes that prove it, and the gates it must pass.

## 0. The finding

**No tool answers Teslon's question.** None says which pages and functions a
PR needs tested, and which it can skip with proof. The best tools each solve
one slice, in one of three ways.

| Approach | Best examples | What it gets right | Where it stops |
|---|---|---|---|
| **Static module graph** | [Chromatic TurboSnap](https://chromatic.com/docs/turbosnap); Playwright `--only-changed` ([PR #31727](https://github.com/microsoft/playwright/pull/31727/files)); [Knip](https://knip.dev/explanations/plugins) | Git diff plus the bundler's import graph gives every story or test that transitively imports a changed file. It is deterministic and cheap. | File level only. Any edit in the graph re-tests, even one that cannot change the UI. A config or `package.json` change re-tests everything. It has no idea of APIs, data or other services. |
| **Contract registries and diffs** | [GraphQL Inspector](https://the-guild.dev/blog/introducing-graphql-inspector) (`diff`, `validate`, `coverage`); [buf breaking](https://buf.build/docs/breaking/) (FILE, PACKAGE, WIRE_JSON, WIRE); [oasdiff](https://github.com/tufin/oasdiff/blob/v1.10.16/BREAKING-CHANGES.md) (100+ OpenAPI checks); [Pact Broker](https://docs.pact.io/pact_broker) (`can-i-deploy`); [Confluent Schema Registry](https://docs.confluent.io/platform/7.2/schema-registry/avro.html) (BACKWARD, FORWARD, FULL) | Exact, field-level answers on whether a contract change breaks a known consumer. GraphQL Inspector checks every client operation against the new schema. | It needs a written schema or contract, and only covers that boundary. It says nothing about pages, data written, or code paths. |
| **Runtime evidence** | [Datadog Test Impact Analysis](https://docs.datadoghq.com/tests/test_impact_analysis/) (per-test coverage); [Launchable](https://launchableinc.com/blog/the-right-tests-for-a-code-change-with-test-impact-analysis) (learned from history); [Sourcegraph SCIP](https://sourcegraph.com/blog/announcing-scip) indexes per commit, for cross-repo navigation | It sees what static reading cannot: reflection, dynamic routes, other repositories. | Datadog's own docs say it can skip tests it should have run: compiler options, external services, data files. Launchable is statistical by design. Neither gives a proof. |

Two research tools come closest to Teslon's back-end half:
- **[Code2DFD](https://github.com/tuhh-softsec/code2DFD)** (TU Hamburg, JSS 2023). It extracts dataflow diagrams from Java microservices with technology-specific extractors: precision 93%, recall 85% on 17 apps.
- **[Prophet](https://github.com/cloudhubs/prophet-utils)** (Cerny's group). It reconstructs the communication diagram of a microservice mesh from static analysis.

Both are diagrams, not test decisions, and neither has a "never silent" rule.

**What "100%" can mean, honestly.** No static tool reaches 100% precision:
reflection, runtime configuration and other repositories are invisible to
it. What we can make 100% by construction is **trust**. Teslon is never
silent and never wrongly skips, because every skip needs a proof, and
anything unproven is held as unclear.

Precision is pushed up with three layers of evidence:
1. **Static proof**, what Teslon does today. Every claim has file and line.
2. **Contracts and registries**: schemas, other repositories' fact files,
   and `catalog-info.yaml`. They turn "outside this repository" into named
   consumers.
3. **Runtime evidence** (optional, offline): OpenTelemetry traces or E2E
   coverage exported from staging. They confirm or add the edges static
   reading cannot see.

Teslon reads them as files. The core stays offline.

## 1. Foundations, before any new stack

These make every later reader cheaper, and keep its accuracy rules in one
place.

| # | Foundation | Why | Borrowed from |
|---|---|---|---|
| F1 | **Facts v2: one fact model for every stack.** It has: Screen, Widget, Call (verb, URL template, payload, result type), Endpoint, Channel (topic, queue, exchange and key, subject), Producer, Consumer, Contract (a type's wire shape), Entity, Write, Read, Job, Guard. Each stack reader emits facts. `where`, `dataflow`, `shape` and `messages` read facts only. | Spring, Vue and Angular are half-way there. React, Kotlin and Node then reuse every analysis instead of re-implementing it. | Code2DFD's technology-specific extractors; Knip's plugins |
| F2 | **Parsers:** <ul><li>the TypeScript compiler for TS, JS, TSX, Next and Nest (already a dependency);</li><li>`@vue/language-core` for typed Vue templates;</li><li>tree-sitter (WASM, offline, deterministic) for Kotlin, Python, C# and Go.</li></ul> The Java reader stays. tree-sitter-java checks it on the history scans. | One parser per language family, each with a clean error path: what it cannot parse becomes "could not see". | [GitHub stack-graphs](https://github.com/github/stack-graphs) (tree-sitter based; archived in 2025, so tree-sitter only, not stack-graphs); [Semgrep](https://semgrep.dev/docs/writing-rules/data-flow/data-flow-overview/) |
| F3 | **A fact file and cache.** `teslon facts --out facts.json` writes one repository's facts at one commit, keyed by file hashes. It is reused across runs and by other repositories. | Speed on monorepos, and the basis of the several-repositories mode. | [SCIP](https://sourcegraph.com/docs/code-navigation/writing-an-indexer) indexes per commit, with nearest-commit fallback |
| F4 | **Adapters: an organisation's own patterns as data.** `teslon.config.json` names its HTTP wrapper (`apiClient.call(method, url)`), its route factory, its message bus. Without an adapter, an unknown wrapper is opaque: the screen is held, never skipped. | Real enterprise code hides calls behind in-house wrappers. Teaching them as data, not code, is how the first answer on a new repository rises above 2.5%. | Knip plugins; Semgrep rules |
| F5 | **An accuracy harness per stack.** Each stack gets a fixture written to its real idioms, a catalog with truth first, history scans of two real repositories, and probes on one real repository. | The ShopFlow lesson: a new stack fails until it is probed. | This project's loop |

**Proof rules.** These cannot be traded away for any stack. A screen or job
may be **skipped** only when all of these hold:
- every file in its module graph was read;
- no import is unresolved, and no import is dynamic with a computed path;
- every network call it makes is resolved to a URL template, or to a named
  operation;
- every changed contract it reads is matched field by field;
- no opaque data source is in its graph (an unknown wrapper, `eval`, a
  global store from a package).

Otherwise it is held, with the reason. The probe harness checks this in every
catalog as `WRONG SKIP = 0`.

## 2. React and Next.js

**Perfect means:**
- every route of a React app is a screen, with its widgets;
- every call each screen makes is known: from the browser, from the server
  (React Server Components, `getServerSideProps`), or through the app's own
  API routes;
- a changed API field lists only the components that read that field, by
  type, as Angular does today.

**Prior art taken:**
- **Knip's Next.js plugin** lists the entry files. This is our route
  inventory:
  - `app/**/{page,layout,template,loading,error,not-found,default}`;
  - `app/**/route`;
  - `pages/**`;
  - `middleware` and `proxy`;
  - `instrumentation`.
- **Next.js 16** renamed `middleware.ts` to **`proxy.ts`**. The `matcher`
  config is unchanged, and without one it runs on every request
  ([nextjs.org](https://nextjs.org/docs/app/api-reference/functions/middleware)).
- **TurboSnap** and **Playwright** confirm that a module-graph walk from each
  route is the base layer. We add calls, data and fields on top.
- **[@vercel/nft](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)**
  is how Next.js traces each route's server files (imports, `require`, `fs`)
  into `.nft.json`. When a build has run, those traces are an optional input
  that proves the server-side graph of each route.
- **[bulletproof-react](https://github.com/alan2207/bulletproof-react)** shows
  the common enterprise layout: features, each with an `api/` folder of pure
  fetchers wrapped by React Query hooks. That is our default idiom.
- **[GraphQL Inspector](https://the-guild.dev/graphql/tools/docs/graphql-tag-pluck)'s
  `graphql-tag-pluck`** pulls Apollo and urql operations out of TSX. It covers
  React apps that call GraphQL.

**Design:**

| Piece | What is read | Notes |
|---|---|---|
| Routes, Next App Router | `app/**/page.*`, segment by segment: groups `(x)` add nothing to the URL, `[id]`, `[...slug]`, `[[...slug]]`, `@slot` parallel routes, `(.)` `(..)` `(...)` intercepting routes | Layouts and templates wrap every page below them: the widgets they draw are on each of those screens. |
| Routes, Next Pages Router | `pages/**`; `_app` is on every page; `getServerSideProps` and `getStaticProps` are the page's server calls | |
| Routes, React Router | v6 and v7: `<Route path element>` in JSX, `createBrowserRouter([...])` with `lazy`, framework mode `routes.ts` (`route`, `index`, `layout`, `prefix`) and route modules (`loader`, `action`, `clientLoader`) ([refs](https://context7.com/remix-run/react-router)) | Loaders and actions are calls made for that route. |
| Routes, TanStack Router | `createFileRoute('/posts/$id')` | As in full-stack-fastapi-template. |
| Calls | `fetch`, axios and axios instances (moved out of the Vue reader into a shared TS module); TanStack Query `queryFn`; SWR keys; RTK Query `createApi` with `fetchBaseQuery({ baseUrl })` and `builder.query({ query })`, and the hooks it generates; generated OpenAPI clients (hey-api, orval), read as code; Apollo and urql operations | Each call is tied to the member that makes it (`ordersApi.cancel`, a hook name), as Vue is now. |
| The app's own back end | Next route handlers (`app/**/route.ts`, `pages/api/**`) and server actions (`'use server'`) are **endpoints of a Node service**. They call the Java APIs onward, through `fetch` to `process.env.X`, read from `.env*` and `next.config` `env`. `rewrites()` in `next.config` is a gateway: `/api/:path*` → the back end. | A page goes to a Next API route, then to Spring: the same chain as page → gateway → service. |
| Proxy and middleware | `config.matcher`, matched against routes like the Vue guards | |
| Widgets | Components drawn by a root layout, or by `_app` | |
| Typed reads | The TypeScript checker on TSX: `order.placedAt` resolved to the declared type, then to the Java DTO through the call's result type | This is the Angular path. JSX is TypeScript, so no template compiler is needed. |
| Server caching | `fetch(url, { next: { revalidate } })`, `cache: 'no-store'`, `export const revalidate` | A change here changes freshness on the page: listed as its own risk. |

**Fixture:** **ShopFlow-Next**. It keeps ShopFlow's back end, and adds:
- a Next.js App Router storefront with API route handlers, server actions,
  `proxy.ts`, `rewrites()`, a root layout navbar, a parallel `@modal`
  route, and React Query in client components;
- a React Router v7 admin console using RTK Query.

**Probes:** about 90, truth first. The Vue probes v01–v25 are mirrored, and
Next-only cases are added:
- server component fetch;
- route handler BFF;
- server action;
- matcher;
- rewrites;
- `revalidate`;
- `generateStaticParams`;
- an intercepted route;
- a layout widget;
- an env-based base URL.

**Real repositories:**
- [opentelemetry-demo](https://github.com/open-telemetry/opentelemetry-demo/tree/main/src/frontend):
  Next.js pages, API routes, gRPC clients in `genproto/`, Cypress e2e;
- bulletproof-react;
- [full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template):
  React, TanStack Router and Query, a generated client;
- [spring-petclinic-graphql](https://github.com/spring-petclinic/spring-petclinic-graphql):
  React, Apollo, Spring GraphQL.

**Gates:**
- T1, T2, T3 and T5 at 0;
- P1 ≤ 5%, P2 ≤ 10%;
- every typed field read resolved on the fixture;
- 0 crashes and 0 citation failures on 60 commits of each real repository.

## 3. Several repositories at once

**Perfect means:**
- when a PR in repository A changes an API field, a topic, a message or a
  proto, Teslon names the consumers in repositories B, C and D, down to their
  pages and jobs;
- when it cannot know them, it says which contract is unaccounted for, never
  "safe".

**Prior art taken:**
- **SCIP.** One index per repository per commit. Cross-repository navigation
  works when both sides are indexed at the right commits; otherwise it falls
  back to the nearest indexed commit, then to search
  ([docs](https://docs-legacy.sourcegraph.com/user/code_intelligence/lsif),
  [commit graph](https://sourcegraph.com/blog/optimizing-a-code-intel-commit-graph)).
  This becomes our fact files (F3), per commit, with the same fallback, said
  out loud.
- **Pact Broker.** A matrix of which consumer version is compatible with
  which provider version; `can-i-deploy` answers "unknown" when no
  verification exists. We take "unknown" as a first-class answer, and the
  idea that the version **deployed**, not the latest source, is what
  matters.
- **Backstage.** `providesApis` and `consumesApis` on `catalog-info.yaml`
  ([API](https://backstage.io/api/stable/interfaces/_backstage_catalog-model.index.ComponentEntity.html)).
  Teslon reads them as hints about which repositories form one system, never
  as proof.
- **[EventCatalog](https://eventcatalog.dev/docs/plugins/asyncapi/intro).**
  Producers and consumers per event, generated from AsyncAPI and OpenAPI.
  These are hints the same way.

**Design:**
1. **A workspace.** `teslon.workspace.json` lists the repositories and the
   ref of each:
   - default branch, or the deployed version, which matters;
   - from a release manifest, Helm values, or a pinned list.

   In CI, the Action checks them out shallow. Locally, it uses
   `--with ../catalog-service`.
2. **Fact files.** `teslon facts` writes each repository's facts on its
   default branch, as a CI artifact or on a `teslon-facts` branch. A PR run
   loads the other repositories' fact files: the CLI fetches them, and the
   core only reads files.
3. **Joining keys** between repositories:

   | Contract | Joined on |
   |---|---|
   | HTTP | service name, or gateway path, plus verb and path template |
   | Kafka and Rabbit | topic, or exchange and routing key |
   | Messages | message type, by its JSON shape, not by class name |
   | gRPC | `package.Service/Method` |
   | GraphQL | `Type.field` |
   | Shared libraries | Maven or npm coordinates and version |

4. **Version skew.** When a consumer pins `shared-events:2.3.0` and the PR
   changes it, the source contract is safe until the consumer upgrades. The
   wire contract on a topic breaks when the producer deploys. Both are said,
   with which comes first: Schema Registry's upgrade-order rule (BACKWARD:
   consumers first; FORWARD: producers first).
5. **No fact file** for a repository the system names: that contract is
   **held**, and the repository is named. That is today's "outside this
   repository", but specific.

**Fixture:** **ShopFlow split.** The same code in five git repositories:
- orders, billing, catalog, notifications;
- web, plus `shared-events` published as a versioned artifact.

**Probes:** about 40. These are:
- the ShopFlow Kafka and Feign probes, with consumers across repositories;
- version-skew probes;
- a fact file missing;
- a fact file stale, with the nearest commit used and said.

**Gate:** no "outside this repository" when the workspace holds the consumer.
Each held contract names the missing repository. Trust gates at 0.

## 4. Live run on real PRs (task 6)

**Perfect means:** the GitHub Action, on a real PR, posts the same answer as
the probe harness:
- within limits: comment size, run time, rate;
- updating its comment on every push, never adding a second;
- safe on forks: a read-only token, so the summary only.

Then real teams' PRs give the number no fixture can: how often Teslon is
right on code it did not grow up with.

**Plan:**
1. **Repositories.** `abhijeet1771/orderdesk` and `abhijeet1771/shopflow`,
   created by you, or by me if the GitHub app is allowed to create
   repositories. Either way, Actions must be on and the Claude app must have
   access.
2. **`bench/live/run.mjs`:**
   - pushes the fixture as `main`;
   - opens one branch and PR per scenario: OrderDesk's 33 proving-ground
     PRs and 30 chosen ShopFlow probes;
   - waits for the Action, reads its comment and summary;
   - scores them with the same rules as the probes;
   - checks re-runs on push, comment update, a fork PR, and a 1,500-file PR.
3. **Field accuracy.** Teslon runs on the last 50 merged PRs of 4 real
   repositories (spm, JHipster, opentelemetry-demo, full-stack-fastapi-template).
   A QA engineer writes truth for 20 of them, blind to Teslon's answer, and
   that gives precision and recall on real PRs. This needs a person: about
   2 hours of a QA engineer's time.

**Gates:**
- the live comment equals the probe harness's answer on every scenario;
- no duplicate comments, and no crash on forks;
- on real PRs: 0 wrong skips, and recall of truth ≥ 95%. We publish whatever
  the number is.

## 5. Field-level precision on Vue

**Perfect means:** a mapper or DTO field change lists only the Vue screens
that read that field. That covers the template, `computed`, a child component
that receives it as a prop, and a store getter. The 7 imprecise ShopFlow
probes become exact.

**Prior art taken:**
- **Vue Language Tools** ([`@vue/language-core`](https://cdn.jsdelivr.net/npm/@vue/language-core@3.3.8/README.md)).
  It generates TypeScript virtual code for each SFC's template and script;
  `vue-tsc` is a thin layer on that. We build the same TypeScript program
  over the virtual code, ask the checker what each property access in the
  template resolves to, and map it back to the template line through Volar's
  source maps.
- **[vue-component-meta](https://github.com/vuejs/language-tools/tree/master/packages/component-meta).**
  The same machinery, used to extract props, events and slots by type. It
  gives the types of `defineProps` for prop drilling, for example
  `OrderLinesTable` taking `lines: OrderLine[]`.

**Design:**
1. **Reads.** Emit `TypedRead`s, the shape `angularReads` already produces:
   - type, property, file, line, expression;
   - the label the template shows.
2. **Into `shape.ts`.** `readsOf` reads Vue as well as Angular. `apiLinks`
   then joins a TypeScript type to its Java DTO through
   `http.get<Order[]>`, the call's result type.
3. **Through stores and composables.** Pinia getters and composable returns
   are typed. A store getter that reads `o.status` is a read of
   `Order.status` for every screen that uses that getter.
4. **When the program does not build** (a missing `tsconfig`, JavaScript
   only): today's behaviour, never worse.

**Probes:** the 7 imprecise ones, plus about 20 more:
- `v-for` item fields;
- props passed down two levels;
- `computed` and `watch`;
- composable returns;
- Options API `data` typed through `defineComponent`;
- JavaScript-only components, which must stay held.

**Gate:** 0 LOUD on ShopFlow; P1 ≤ 3%.

## 6. RabbitMQ, Spring Cloud Stream, GraphQL, gRPC, WebFlux, Spring Batch

All map onto the Channel and Contract facts of F1.

| Technology | What perfect needs | Prior art and the rule we take | Design notes |
|---|---|---|---|
| **RabbitMQ** | A producer's exchange and routing key go to every queue bound to it, and on to its listeners | [Spring AMQP](https://docs.spring.io/spring-amqp/api/org/springframework/amqp/rabbit/annotation/QueueBinding.html): `@QueueBinding(value, exchange, key)` with multiple keys; `BindingBuilder.bind(q).to(topicExchange).with("foo.*")`; topic wildcards `*` (exactly one word) and `#` (zero or more) | <ul><li>Bindings are read from `@Bean` Queue, Exchange and Binding, `Declarables`, `@RabbitListener(bindings=…)`, and `spring.rabbitmq.template.*`.</li><li>The default exchange routes by queue name. Fanout goes to every bound queue.</li><li>A headers exchange, or a key built at runtime, makes the listeners held, not skipped.</li></ul> |
| **Spring Cloud Stream** | A function's binding goes to its destination and group, whichever binder | [Reference](https://docs.spring.io/spring-cloud-stream/reference/spring-cloud-stream/event-routing.html): `spring.cloud.function.definition`, bindings `fn-in-0` and `fn-out-0` with `destination` and `group`; `StreamBridge.send(...)` | `Function`, `Consumer` and `Supplier` beans are read with their bindings. `StreamBridge.send(name)` goes to a binding by that name if one is declared, else to a destination; this is checked against the docs while it is built. It lands on the same Channel as Kafka and Rabbit. |
| **GraphQL** | A schema field change lists the operations that select it, and the screens that run them | [GraphQL Inspector](https://the-guild.dev/blog/introducing-graphql-inspector): `diff` marks every change breaking, dangerous or safe; `validate` checks documents; `coverage` maps fields to operations; `graphql-tag-pluck` pulls operations from TS and Vue | <ul><li>Server side: Spring GraphQL `*.graphqls` and `@QueryMapping`, `@MutationMapping`, `@SchemaMapping`.</li><li>Client side: `gql` operations in components.</li><li>The breaking and dangerous classes are Inspector's.</li></ul> This is more precise than REST, because each operation names its fields. |
| **gRPC** | A proto change lists every server and client of that method in every language, and the screens behind the BFF | [buf breaking](https://buf.build/docs/breaking/): WIRE_JSON is the minimum when clients use gRPC JSON or Connect; WIRE when binary only | <ul><li>`.proto` files are parsed (protobufjs, offline).</li><li>Servers: `XxxImplBase`, `@GrpcService`, Go `RegisterXxxServer`, Node `addService`.</li><li>Clients: stubs.</li><li>Changes are classed as buf's.</li></ul> The opentelemetry-demo frontend reaches gRPC through Next API routes: the chain is page → route → gRPC → service. |
| **WebFlux functional routes** | `RouterFunction` routes are endpoints like `@GetMapping` | Spring docs: `RouterFunctions.route().GET(…)`, `.nest(path(…))`; Kotlin [`coRouter { GET(…) }`](https://docs.spring.io/spring-framework/docs/current/kdoc-api/spring-webflux/org.springframework.web.reactive.function.server/co-router.html) and `nest` | Each route becomes an Endpoint whose handler is the method reference. Everything downstream is reused. |
| **Spring Batch** | A job's step writers are writes, its triggers are its start, and the job is an area | `JobBuilder`, `StepBuilder.chunk(reader, processor, writer)`; `JdbcBatchItemWriter` SQL, `JpaItemWriter`, `RepositoryItemWriter` | <ul><li>Jobs become `job:batch:<name>`.</li><li>Writers become entity writes, which lead to the screens that show them.</li><li>Triggers (`@Scheduled` + `JobLauncher`, `spring.batch.job.name`, an endpoint) are calls.</li></ul> |

## 7. Kotlin, then back ends that are not Java

**Kotlin.** tree-sitter-kotlin
([fwcd](https://github.com/fwcd/tree-sitter-kotlin), built from the official
grammar, WASM build) reads Kotlin into **the same model the Java reader
produces**, so every Spring rule applies unchanged. What is new:
- data classes: the primary constructor holds the fields and the JSON;
- `const val` and companion objects: the constants for topics;
- annotation use-site targets: `@field:JsonProperty`, `@get:`;
- `"\${…}"` inside annotations;
- extension functions;
- named and default arguments;
- nullable types: a field made nullable is a contract change;
- `kotlinx.serialization` `@SerialName`;
- Spring Kotlin DSLs: `beans {}`, `router {}`, `coRouter {}`.

The grammar was last pushed in April 2025 and annotations are a known
ambiguity. Anything it cannot parse is "could not see"; the history scans
catch it.

- **Fixture:** ShopFlow's billing and notification services rewritten in
  Kotlin, so the repository mixes languages, as real teams' do.
- **Real repositories:** spring-petclinic-kotlin, and opentelemetry-demo's
  fraud-detection (Kotlin, Gradle KTS, consumes Kafka).

**Back ends that are not Java,** in order of how often enterprise front ends
call them:

|---|---|---|---|---|---|---|
| 1 | Node: NestJS, Express, Fastify | TypeScript compiler | `@Controller` and `@Get` decorators; `router.get` with router mounting; Next route handlers (§2) | class-validator DTOs, zod schemas, TS types | Prisma (`schema.prisma` is the entity list), TypeORM, Sequelize | kafkajs, amqplib, BullMQ |
| 2 | Python: FastAPI, Django + DRF | tree-sitter-python | `@app.get` and `APIRouter` prefixes; `urls.py` with viewsets | Pydantic models, DRF serializers | SQLAlchemy, SQLModel, Django ORM; Alembic and Django migrations | aiokafka, Celery |
| 3 | .NET: ASP.NET Core | tree-sitter-c-sharp | `[HttpGet]` attributes, minimal APIs (`MapGet`) | records and `[JsonPropertyName]` | EF Core entities and migrations | MassTransit; eShopOnContainers' event bus over RabbitMQ |
| 4 | Go: net/http, chi, gin, echo | tree-sitter-go | route registration calls | structs with `json:` tags | GORM, sqlc | sarama, segmentio/kafka-go |

| Iterations 10–11 | React and Next.js (§2), F4 adapters | — | about 68 → 74 (front ends 4 → 8, first answer 5 → 6) |
| Iteration 12 | Field accuracy on real PRs (§4, step 3) | 2 hours of a QA engineer, writing truth for 20 PRs | Part 9: 3 → 4; the first real recall number |
| Iteration 13 | Several repositories (§3) | — | about 74 → 78 |
| Iteration 14 | Rabbit, Stream, GraphQL, gRPC, WebFlux, Batch (§6) | — | about 78 → 82 |
| Iteration 15 | Kotlin (§7) | — | about 82 → 83 |
| Iterations 16+ | Node, then Python, .NET, Go (§7) | — | about 83 → 88–90 |

The last 10% is the long tail:
- mobile clients;
- in-house frameworks without adapters;
- code built at runtime.

There, Teslon's job is to say clearly what it could not see.

**What stays the same through all of it:**
- the core never touches the network;
- every claim has file and line;
- every new reader comes with a fixture, a truth-first catalog and real
  history scans before it is called done;
- a gate that fails blocks the release.

CodeQL has the deepest data flow, but it is not embedded. Its CLI is free
only on public repositories; private ones need GitHub Code Security
([docs](https://docs.github.com/en/enterprise-server@3.9/code-security/codeql-cli/getting-started-with-the-codeql-cli/about-the-codeql-cli)).
That fits neither an offline tool nor every team's licence.
