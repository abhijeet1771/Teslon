# Review: the plan and the impact cockpit, by the people who would use them

2026-11-03. This review covers four things:
- the cockpit mock (`research/sample-output/report-cockpit.html`), opened in a real browser at 1440×900 and 390×844, with every tab clicked;
- what the engine prints today (`teslon impact`);
- the setup, timed from a fresh clone;
- the plan (`ROADMAP.md`, `research/WHAT-TO-TEST.md`).

It is read from the point of view of each person who would touch it.

## Verdict in one paragraph

The idea and the evidence model are strong, and nothing on the market does
page → field → value → expected result with every line re-checked. But today
there are two products that do not meet. The cockpit is a beautiful static
mock with hard-coded data. The engine is real, but it prints long terminal
text, needs a local clone and two commit hashes, and has a README that
describes the older engine. A QA engineer cannot get the cockpit for their own
PR today. The next step that matters most is not another rule. It is joining
the two: PR link in, cockpit and PR comment out, from the real engine's JSON.

## Setup

What a person has to do today:

1. Install Node 20+.
2. Clone Teslon.
3. Run `npm install` and build (7 s once dependencies are cached).
4. Have a clone of their own app with the history of both commits.
5. Find the base and head commits.
6. Run `node …/cli.js impact <base>..<head>`.

Problems:

- **The input is two commit hashes, not a PR link.** Nobody in QA has these.
  `teslon pr <url>` with patch-id recovery is on the list but not built.
- **There is no `npx teslon`**: the package is not published.
- **No GitHub Action or App posts a comment** or a check.
- **Two engines live in one CLI.** `help` lists 8 commands (`impact`, `pr`,
  `merged`, `analyze`, `profile`, `paths`, `cases`, `changed`, `java`). Only
  `impact` is the new engine. A first-time user cannot tell which to use.
- **The README describes the old engine** (bands, tiers 1–4, radius), not
  `teslon impact`.
- **`teslon ui` serves the old engine's report.** The cockpit is not wired to
  anything.
- **Setup succeeds in seconds**, which is good. The cost is not install time.
  It is that the person who needs the answer is not the person who can run
  it.

## Look and feel (cockpit)

What is good:

- **Verdict first, in five numbers.** Skip "with proof" and unseen "said out
  loud" are shown next to "test", which is rare and builds trust.
- **The app map is grouped by module, with a count per screen**, so a lead
  can see the shape of a release in five seconds.
- **The screen detail is the best part.** It shows test first, DO, a
  before/after diff of experience, and evidence that folds open with
  verified/derived per hop.
- **Conflicts between changes** ("only today can be chosen") are something no
  other tool shows.
- **"Example data · shows scale"** is labelled honestly.
- **It works on a phone** with no horizontal overflow.

What to fix:

1. **Three dense columns at once.** A first-time user does not know where to
   start. Add one "Start here" strip: the top 3 cases, then "see all".
2. **Colour meaning.**
   - Red for "test 32" reads as failure. Use a neutral strong colour for
     work to do; keep red for "breaks" and conflicts.
   - Matrix cells are red, orange and dark grey with no legend, which is
     colour-only meaning (colour-blind users lose it). Add a legend and a
     shape or letter per cell.
3. **Small text.** 56 text elements are under 11 px (file:line, hop labels,
   counts), and `<html lang>` is missing. Make 12 px the floor and set the
   language.
4. **Jargon.**
   - "Nothing printed until both ledgers balance", "derived", "unseen" and
     "rule hole" are engine words. Say "every changed line is accounted
     for", "follows from the code (not run)", "Teslon could not see" and
     "still lets through".
5. **The test plan repeats itself.**
   - "because …" is repeated on every card.
   - The same screen appears several times. Group by screen, then by field,
     and keep the reason as one line per group.
6. **No time.** "49 cases" means nothing to a manager. Show an estimate
   (cases × a team's average minutes, editable) and a risk level.
7. **On a phone, the changes list comes first.** A tester on a phone wants
   the test plan first.
8. **The matrix**:
   - It is impressive but hard to read: rotated labels and tiny cells.
   - Make it secondary (a "for leads" view).
   - Sort columns by how many changes meet there, and show the column name
     on hover/tap.
9. **The checkbox state** must persist and be shareable: "who tested what, on
   which build". Otherwise the plan is copied into another tool and Teslon is
   forgotten.
10. **One demo toggle at the top** ("Large AI PR · example" / "PR #559 ·
    real") belongs to the pitch, not the product. The product opens on the
    user's PR.

## The terminal report (what exists today)

- It is correct and verifiable: 70/70 lines re-read on #559, and 0 evidence
  failures over 60 real commits.
- It is long: about 110 lines for a 3-file PR. It speaks in hops ("path: ✓
  api … → ✓ gateway …"), which developers like and testers skip.
- What is needed:
  - a 5-line summary block on top for a PR comment;
  - `--brief` for testers (screen, field, do, expect only);
  - the current output kept as `--evidence`.

## The plan

What is right:

- Evidence by construction, never silent, measured on a bench with an
  independent oracle.
- Breadth ("where", for every PR) before more depth: real history showed 3
  of 60 commits covered before, and 36 of 60 after.
- Spikes before adopting tools: smart-doc was rejected because it silently
  missed a rename.

What I would change:

1. **Ship a thin end-to-end slice before more rules:**
   PR link → engine JSON → cockpit HTML + PR comment, on Spring + Vue/Angular.
   Today the plan puts outputs last ("polish only on top of measured
   accuracy"). But without a surface nobody uses it, and without users
   there is no feedback and no escapes to learn from.
2. **React and Node earlier.** React and Next.js are what most teams run.
   Stage 8 is too late if adoption matters. Pick stacks by the first
   design partner.
3. **Accuracy needs a number before anyone is shown one.** One independent
   case is an anecdote. 30+ oracle cases across 3 apps is the first defensible
   scorecard. It is also what a manager will ask for first.
4. **Bring the QA's real unit forward:** the build (everything since the last
   tested deploy), overlap between PRs, and reverse lookup ("bug on /checkout,
   which change?"). These turn a PR toy into a release tool.
5. **A feedback button on every case**: "wrong", "missed", "useless". Each
   escape becomes a bench case. That is the learning loop the plan already
   names and has not scheduled.
6. **Keep what v1 already has:** owners and effort. The new report dropped
   them.

## Questions nobody has answered yet

1. **Who is the first user, and where do they work all day:** GitHub, Jira,
   TestRail, Slack? This decides the delivery surface more than any rule.
2. **Is the unit of work the PR, the build, or the release?**
3. **When does it run:** on every PR, on merge, or on each deploy to staging?
   And who presses the button?
4. **Where does the code go?** Local, the customer's CI, or a hosted service.
   Offline-by-design is a selling point; a hosted app would give it up.
5. **Which stacks first**, chosen by a real design partner rather than by
   petclinic?
6. **What does success mean, measured:** fewer escaped bugs, less test time,
   fewer "what should I test?" messages? Take a baseline before rollout or
   it can never be shown.
7. **Most teams already have a manual test-case library.** Should Teslon say
   "rerun these 12 existing cases in TestRail" instead of only writing new
   ones?
8. **Several repos:** microservices across repos, a separate mobile app, a
   config repo. Who connects them, and how?
9. **Changes outside code**: data fixes, flag flips, config in another repo,
   infrastructure. Do they enter as "changes" too?
10. **Huge AI-generated PRs:** what does the first screen say when 400 files
    changed? (The regression grouping is a start.)
11. **Sign-off and audit**: a record of who decided to skip what, per release.
12. **Packaging and price:** open-source CLI plus a paid team surface? A
    manager will ask.
